Technical tour

One control plane, many disposable runners.

Chetter is intentionally boring: one Go server, one SQL database, a ConnectRPC runner protocol, and ordinary container images. The interesting part is how these pieces combine into durable agent automation.

System map

The server owns state. Runners own execution.

This split keeps the control plane understandable and lets you scale by adding server replicas, runner containers, or Kubernetes workloads — all coordinated through the database alone, with no Redis or external pub/sub.

Server

Go MCP + web UI

Exposes /mcp, GitHub webhooks (with delivery queue, retries, idempotency, and dead-lettering), ConnectRPC endpoints, trigger scheduling and manual trigger test runs, event callbacks, managed Git identities, API tokens with configurable expiry, model catalog, definitions sync (scoped to global/, groups/, repos/), MCP endpoint resolution, agent catalog API, execution attempt tracking, audit log, graceful shutdown, /healthz and /readyz probes (the latter performs a database ping for Kubernetes readiness), /api/server-info reporting server version, git hash, and uptime, a Prometheus /metrics endpoint with task, runner, and webhook gauges (optionally gated behind a bearer token via CHETTER_METRICS_AUTH_TOKEN), and embedded SvelteKit UI. The server version is injected at build time from git describe via Makefile ldflags (defaulting to dev), and a GitHub Actions release.yml builds chetter/chetterctl binaries for linux/amd64 and darwin/arm64 on v* tags, creating the GitHub release with notes pulled from the matching ## [x.y.z] CHANGELOG section.

Database

TiDB, MySQL & PostgreSQL

Stores tasks, leases, events, triggers, sessions, checkpoints, runners, teams, API tokens, git identities, definitions, audit events, artifacts, searchable text — and the coordination tables (claim_notify_counter, trigger_locks, admission_locks, runner_drain_requests) that let several server replicas share one control plane without Redis.

Runner

Harness controller

Claims work, prepares a workspace, starts the chosen harness, supervises timeouts, streams events, reports resource snapshots (CPU, memory, disk) on heartbeat, handles SIGTERM via timeout-aware drain (pauses resumable sessions on force-cancel), and cleans up containers and workspaces.

Agent image

Project runtime

Language/tooling images inherit from the agent base and run OpenCode, Claude Code, Codex, Pi, or CodeWhale against the mounted workspace.

MCP

AI-facing control surface

Tasks, triggers, sessions, runner health, GitHub artifacts, definitions, aggregate cost and token summaries, and admin actions are exposed as schema-driven MCP tools.

ConnectRPC

Runner protocol

Runners use RegisterRunner, Heartbeat, ClaimTask, and ReportTaskEvents. Cancel and drain commands return on heartbeat responses.

Web UI

Human operations

The UI uses ConnectRPC to show tasks, triggers, runners (with per-runner CPU, memory, and disk utilization bars), sessions, audit events, artifacts, agent definitions (browsable catalog with per-agent activity), and aggregate task activity with server-side team/repo filtering. Task pages surface full configuration — provider, model, harness, session mode, git ref, skills, and environment — plus deadline extension with URL state persistence. The Recover action opens a prompt editor pre-filled with the default recovery instruction, so operators can steer a recovery with their own follow-up prompt. Resuming a paused or recoverable session navigates the operator straight to the new attempt's task detail page — which already streams live progress, events, and — while the task runs — a live Execution card showing the current runner's CPU/memory/disk gauges, sandbox status, and sandbox timing and counters — instead of silently staying on the session page; the resume form is disabled while the request is in flight, duplicate submissions are guarded, and backend validation or runner-availability errors surface inline in the resume modal. Trigger detail pages offer a Test Trigger action for pr_review and issue triggers — it simulates a webhook event (repo, action, PR/issue number, optional labels), fetches authoritative metadata from GitHub, and dispatches through the same matching and task configuration as a real delivery, stamping test-originated tasks submission_source=trigger_test with a trigger_test_run audit event. Token management pages include expiry configuration and visual expiry badges. The UI footer shows the running server version as x.y.z-githash with live uptime, reported by /api/server-info. The server itself is hardened for exposure: OIDC sessions are HS256-only with issuer and expiry validation and config-derived secure cookies (__Host-chetter-session on HTTPS, SameSite=Strict), login endpoints are per-IP rate limited, responses carry a CSP with script hashes computed from the served index.html (no unsafe-inline) plus X-Frame-Options, nosniff, and HSTS on TLS, and browser token login can be disabled entirely via CHETTER_ALLOW_TOKEN_LOGIN.

Queue semantics

The task queue is just SQL plus leases.

No separate broker is required. The database is the source of truth for pending work, ownership, attempts, terminal state, and event history.

A
Claim safely

SELECT ... FOR UPDATE SKIP LOCKED finds claimable work. The winner sets status=running, runner_id, claimed_at, started_at, and a lease expiry.

B
Renew cheaply

Heartbeats refresh leases for the runner's current task ids and return commands such as cancel or drain.

C
Recover predictably

The reaper runs every 30 seconds. Expired leases create a fresh execution attempt on reclaim, restarting the agent session with the previous attempt's context. Tasks that exhaust max_attempts (default 5) are marked error with a timeout category. Each execution attempt is a separate row in the execution_attempts table, giving operators a clear retry trail. The reaper recovers from panics so one bad pass never kills the loop, and it stamps a lastReapAt health signal on /api/server-info so operators can spot a stalled reaper. Auto-recovery can be disabled entirely via DEFAULT_AUTO_RECOVERY=false, and the reaper skips tasks whose runners were deliberately drained, preventing silent re-queue during operator-initiated maintenance. Expired leases from draining or stopped runners fail permanently instead of being retried.

D
Extend deadlines

Operators can add time to a pending or running task from the web UI. ExtendTask bumps timeout_sec in place and records a task_timeout_extended audit event — no restart or resubmission required.

E
Pause and resume

Tasks with session_mode: resumable create a checkpoint-backed session. Sessions are task-owned and track each user prompt in sequence. chetter_resume_agent_session appends a follow-up prompt and queues a new execution attempt in the same session — the web UI then leads the operator straight to the new attempt's live task page. chetter_recover_task recovers terminal tasks in fresh agent sessions using the previous session export as context, optionally with a custom prompt used verbatim while the prior export stays attached as a recovery file — each recovery creates a new execution attempt, preserving the full retry history.

F
Re-run terminal tasks

chetter_rerun_task clones a terminal task (done, error, or cancelled) into a fresh task with the same prompt, git repo, model, agent, harness, skills, and environment — without changing the original. The web UI exposes a one-click "Re-run" button on task detail pages, so operators can retry a failed or finished task instantly. Re-runs carry the same team scope and trigger attribution as the original task.

Execution modes

Serve mode and RPC mode

OpenCode, Claude Code (serve-proxy), CodeWhale, and Codex (App Server proxy) harnesses expose an HTTP serve API for streaming, session management, and prompt dispatch. OpenCode implements CompletionAwareHarness — it dispatches prompts asynchronously, detects session completion via SSE session.status idle events, and falls back to polling, so long-running tasks survive proxy timeouts or network drops. Claude Code's serve-proxy now matches that parity: it parses real provider errors out of stream-json results (instead of reporting a failed turn as success), accounts cache tokens, streams subagent text and hook lifecycle events, exposes a GET /session/{id}/status probe that tells a hung generation from a finished turn, and continues idle sessions via POST /session/{id}/continue — running with --permission-mode dontAsk and strict MCP loading (--mcp-config --strict-mcp-config) so a cloned repository cannot register its own MCP servers, with a configurable turn cap (CHETTER_CLAUDE_MAX_TURNS, default 500) and an optional spend ceiling (CHETTER_CLAUDE_MAX_BUDGET_USD). Pi uses RPC mode with JSONL events over stdio, parsing cumulative usage (input, output, cache read/write, reasoning, and dollar cost) with per-message deltas so interrupted streams never double-count, publishing keepalive progress during silent stretches, verifying the requested model against Pi's get_available_models response, and streaming thinking deltas as progress. Streaming events are accumulated and flushed in short publish windows, and the runner normalizes every harness into the same task events.

Watchdog

Stalled harnesses are nudged, not killed

A progress watchdog classifies silence before acting: OpenCode and Claude Code report session state through a status probe (a busy in-flight turn is tolerated for a bounded window instead of being nudged mid-generation), and Pi's get_state probe classifies isStreaming/isCompacting/pendingMessageCount into busy or idle, with probes routed back through an RPC probe hub on their own goroutine. An idle-but-stalled agent is nudged with a continuation prompt (OpenCode/Claude Code resume-based, Pi's native post-turn follow_up); real harness progress resets the per-stall streak so an agent that stalls, recovers, and stalls again later gets a fresh budget, and an absolute cap of 10 continuation prompts bounds harnesses that only move when prodded. Terminal stuck errors carry quantified diagnostics — silence duration, prompt totals, last event, turn state — and a stuck Pi harness is interrupted and reported as a quantified "stuck harness" error rather than hanging.

Task setup

Personas and skills injected per harness

Git-backed agent and skill definitions are materialized into each harness's native layout before the agent starts: .claude/agents/ and .claude/skills/ for Claude Code (personas appended via --append-system-prompt-file so they compose with Claude's built-in prompt), .pi/skills/<name>/ plus a task agent definition passed via --system-prompt for Pi, and the equivalent paths for OpenCode — extracted by a shared skilltar package. Every runner-owned config file containing capabilities or credentials (settings.json, .pi/settings.json, models.json, .mcp.json, .claude/chetter-mcp.json) is written mode 0600.

Execution backends

Docker containers or Kubernetes Pods

Each task runs either as a Docker container (with an optional runsc gVisor sandbox) or — when execution.backend: kubernetes is set — as an independent Kubernetes Pod. The KubernetesExecutor owns the pod lifecycle: creation, readiness polling, log and workspace-event streaming, cleanup, and task-event forwarding. Pod execution is configurable per runner via namespace, runtime class (gVisor through kata or run.kata), image pull policy, service account, workspace PVC or hostPath, node name, and pod readiness timeout, generated from runner env vars. Both backends normalize to the same task events, so the control plane is agnostic to where the work ran. In Kubernetes mode the runner deployment is protected against needless pod churn and mid-task termination: a PodDisruptionBudget (minAvailable: 1) gates voluntary evictions (node drains, autoscaler scale-down, cluster upgrades), terminationGracePeriodSeconds: 120 gives the default 30s drain plus 60s hard-kill barrier room to finish with margin, a maxSurge: 1 / maxUnavailable: 0 rolling strategy brings a replacement runner Ready before the old pod terminates, and topology spread constraints plus the safe-to-evict: "false" annotation round it out. Node failure, OOM, and spot reclamation still kill the runner pod; the reaper then re-queues its tasks after lease expiry.

Isolation

Workspace + container sandbox + egress filtering

Docker mode bind-mounts the workspace into /workspace. gVisor (runsc) is the sandbox boundary: a userspace kernel (the Sentry) intercepts every syscall the container makes and implements the Linux ABI in userspace, so the agent never touches the host kernel. Plain Docker (runc) and local execution are convenience modes for trusted workloads — not a task security boundary. Outbound traffic is routed through transparent HTTP and DNS proxies on the runner that enforce a domain allowlist; this is an operational egress control, not a network security boundary (gVisor sandboxes the agent process, not the network or the MCP bridge). gVisor DNS is forwarded so endpoint hostnames resolve inside sandboxed containers. Optional CPU, PID, and memory caps (CHETTER_CONTAINER_CPU, CHETTER_CONTAINER_PIDS, CHETTER_CONTAINER_MEMORY) bound a single runaway task from exhausting the host, applied consistently across the serve and RPC harness paths. Task containers run with all capabilities dropped (--cap-drop ALL) and no-new-privileges; Kubernetes task pods additionally disable service-account-token automount, and the MCP server container runs non-root. The agent base image pins its gh, Node, and OpenCode downloads with SHA-256 verification and pins the remaining harness CLIs via build args.

Diagnostics

Failures keep evidence and classification

Transport failures capture container state, HTTP probes, and log tails. Structured task-level failure categories (timeout, harness_error, runner_lost, internal_error, user_cancelled, quota_exceeded, resource_limit, unknown) let operators quickly triage why a task failed without digging through event logs. The web UI displays the failure category directly on task cards and detail pages. Recoverable failures can preserve workspaces and session exports for follow-up tasks, and cancellation flushes the harness and reads the final export before the container is stopped, so cancelled resumable sessions keep their work.

Resilience

Graceful shutdown, failure isolation, and data lifecycle

The server stops accepting new connections on SIGTERM, drains in-flight webhook goroutines, stops reaper/cron/sync loops mid-cycle, closes the database, and exits 0. A second SIGTERM during the drain forces exit 1. The runner marks itself draining, stops claiming new tasks, waits for in-flight tasks (up to CHETTER_DRAIN_TIMEOUT_SEC, default 30s), and force-cancels any that overrun — pausing resumable sessions so they can resume on a fresh runner. After the drain deadline the runner blocks exit until every task's teardown (sandbox teardown, workspace destroy, session-export flush) and terminal ReportTaskEvents delivery complete, bounded by CHETTER_DRAIN_HARD_KILL_TIMEOUT_SEC (default 60s, replacing the old CHETTER_DRAIN_CLEANUP_GRACE_SEC), so rolling deploys never lose terminal results mid-report; a hard-kill audit log lists in-flight executions and their report-delivery status. Webhook events are persisted to webhook_deliveries with idempotency deduplication and retried with exponential backoff (1s/5s/15s) before dead-lettering after 3 attempts. The chetter_list_webhook_deliveries MCP tool lets operators inspect delivery status, attempts, and errors.

Database operations transparently retry transient errors (connection refused, broken pipe, leader change) with exponential backoff, so network blips never cascade into task failures — non-transient errors like syntax or auth rejections propagate immediately. Task environment variables are validated at submission time: dangerous prefixes (CHETTER_, RUNNER_, MCP_AUTH, DATABASE_, GITHUB_APP_, ARCANE_, LLM_) and reserved system names (PATH, HOME, SHELL, LD_PRELOAD, LD_LIBRARY_PATH) are rejected, preventing configuration injection. Beyond environment variables, task and trigger fields are validated centrally at the single submission chokepoint shared by MCP, the web UI, and webhooks: the harness must be a supported one or the runner default, session_mode must be none or resumable, timeout_sec and ttl_hours stay within operator-configured caps (CHETTER_MAX_TASK_TIMEOUT_SEC, CHETTER_MAX_SESSION_TTL_HOURS), and GitHub trigger repos use canonical owner/repo syntax — invalid requests are rejected before any persistence. Secret redaction is a second boundary: before any runner output is stored or published, exact known secret values — built per execution from designated sensitive environment variables (keys containing SECRET, TOKEN, KEY, or PASSWORD) — are replaced with [REDACTED] across event payloads, summaries, session exports, callbacks, and live publication; the in-memory set is never logged, audited, or persisted and is discarded when the session ends. Configurable TTL-based storage pruning lets operators set retention policies (EVENTS_RETENTION_DAYS, AUDIT_RETENTION_DAYS, ARTIFACT_RETENTION_DAYS) to clean up old rows from high-growth tables — task_events, audit_log, task_artifacts, and agent_sessions — in batched delete operations that avoid long-running transactions, with all defaults at 0 (off) so existing deployments are unaffected until an operator opts in.

Scaling

Multi-replica coordination — database only

The server scales horizontally across replicas with no Redis and no external pub/sub; the database is the coordination layer, in five tiers. Claim wake-up bumps a claim_notify_counter row that each replica polls once per second, so idle runners wake within ~1s of a task being created by any replica instead of waiting out the 15s safety-net poll. Cron deduplication locks trigger_locks rows with SELECT ... FOR UPDATE and persists a last_triggered_at interval marker, and each run re-checks the persisted enabled flag, so enable/disable/delete converge across replicas within one tick. Strict pending admission runs the pending count and the insert in one READ COMMITTED transaction guarded by an admission_locks row lock, so concurrent replicas cannot overshoot CHETTER_MAX_PENDING_TASKS. Drain commands are persisted in runner_drain_requests and delivered at-least-once on every heartbeat until the runner reports a draining status (the ack), with unacknowledged rows dropped after 30 minutes and drain_runner failing closed on database errors. And task-event and fleet streams poll the database every 1s alongside the local event bus, so events committed by another replica reach connected clients within 1–3s, degrading gracefully on transient database errors instead of disconnecting viewers. Known limitations are documented rather than hidden: redaction sets are per-replica and cache-only, event cursors are timestamp-based, and trigger toggles are eventually consistent.

Definitions

Scoped Git-backed configuration

Agent markdown, skills, triggers, task templates, MCP endpoints, and model catalogs sync from Git every five minutes. Definitions are organized under explicit scope directories — global/, groups/<team>/, repos/<owner>/<repo>/ — that control visibility. Global definitions are available to all teams; team-scoped definitions are only visible to that team's tokens, and cross-team names resolve as not-found so one team's task can never receive another team's agent or skill definition. Definitions are materialized and validated before use.

Model catalog

Provider details stay data-driven

The catalog resolves provider id, model id, base URL, API key env var, provider kind (openai_compatible, native, aws_bedrock), and per-harness API transport before the task reaches a runner. One logical provider — a LiteLLM router, for example — can map to different wire protocols per harness (OpenAI completions, Anthropic messages, or Responses API) with no code changes.

Cost & Audit

Full audit trail with cost tracking

Every server action is logged with event type, source, target, repo, token identity, and searchable detail. Aggregate token usage and cost summaries group by team, trigger, or repo across configurable time windows. The web UI filters, toggles, and searches the trail in real time.

Releases

Versioned binaries on every tag

Releases are tagged with a v* version. The release.yml workflow runs the full make check suite — which now includes a dual-dialect SQL parity guard that fails the build whenever the MySQL/TiDB and PostgreSQL query sets drift apart, and verifies every query is materialized in the generated repositories and the internal/data/ facade — plus the PostgreSQL test matrix, then builds chetter and chetterctl for linux/amd64 and darwin/arm64 (with the version embedded via ldflags) and attaches them to a GitHub release. Release notes come from the matching ## [x.y.z] CHANGELOG section, falling back to GitHub-generated notes when the section is missing. The running server identifies itself with version, git hash, and uptime through /api/server-info and the UI footer.

MCP Endpoints

External tool integration

Agent definitions reference named MCP endpoint definitions synced from the config repo. At claim time the server resolves URLs, headers, and bearer-token credentials, then delivers endpoint tokens to the runner. Each harness — OpenCode, Claude Code, CodeWhale, Pi, and Codex — receives native MCP configuration. Tokens are validated and protected from task overrides, keeping secrets out of task payloads. Chetter MCP traffic routes through a runner-local reverse proxy so task containers access the server at a consistent endpoint; the relay authenticates internal requests, and OpenCode re-applies the runner-configured server settings after cloning the repository to prevent config hijacking. OAuth is explicitly disabled for the Chetter MCP connection so non-interactive runners never block on an OAuth flow. gVisor DNS is routed through the runner so endpoint hostnames resolve inside sandboxed containers.
